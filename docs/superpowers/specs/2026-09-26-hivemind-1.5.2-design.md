# Hivemind 1.5.2: project capabilities, agent identity and console

Status: design approved in conversation on 2026-09-26. Implementation follows adversarial review.

## Purpose and boundaries

Ship version 1.5.2 with a visible server version, usable project capability and per-agent settings screens, truthful model reporting, and one canonical `claude` client identity. Project users—not agents acting through supported MCP tools—define capabilities and assign them to agents. Preserve existing `claude-code` work and allow old clients to reconnect. Update the Claude and Codex instructions so agents can request a missing file from a peer after checking the graph. This release does not add file transport, new token types, a limit on running sessions, or longer chat retention.

The existing user token continues to authenticate both the UI and agents. Consequently restricting supported MCP mutations is a workflow guarantee, **not** a hard security boundary against an agent deliberately using the UI HTTP API with the same token. Do not claim otherwise in docs or error messages.

## Capability governance

Use the existing project-local capability catalog and agent settings storage. Extend catalog definitions with an explicit approval state and migrate preexisting definitions: legacy auto-created/empty-description rows begin **pending**; previously human-defined descriptions begin approved. Pending definitions are visible for review, not silently removed. Project users may create or approve definitions with nonempty descriptions, update descriptions, and manually assign/revoke approved tags from a specific stable agent address. Existing agent-side tags whose grants were not explicitly managed by a project user begin **pending per-agent assignment** even if their definition is approved. Approving a definition never approves its preexisting agent assignments. Preserve pending tags for review, and require explicit project-user confirmation for each agent; normal agent reads distinguish approved and pending tags. An agent that considers an assignment inaccurate asks a project user to correct it.

An agent's supported MCP capability tools are read-only for grants and definitions; `agent_capabilities_set` must return a clear refusal without changing state. `agent_config_update` may still change the agent's own max-parallel-tasks and auto-claim settings, but any capability-grant parameter is rejected (not ignored). Other agent MCP calls must not create catalog rows indirectly, including task offer/enable/requirements. A task may require only an approved, existing catalog tag; an agent can claim or be assigned eligible work only if **all** required definitions and that agent's assignments are approved. The check is enforced on the server at discovery, assignment and claim, not solely in the UI. Existing queued assignments requiring unapproved tags remain visible but cannot be claimed until an authorized project user approves the definition and the per-agent grant. An already-live claim keeps its current lease and can heartbeat, finish or expire normally; approval migration must not silently revoke it. Once that claim ends, a fresh claim uses current eligibility. Explicit removal of an approved grant retains the existing immediate fencing behavior.

The UI uses project-scoped user authorization and existing revision/compare-and-swap checks for catalog and agent edits. Editing a description alone must not auto-grant a tag. Notify an affected agent of an assignment/config change via the existing durable DM path; show a warning if the edit committed but notification failed. Catalog and pending-assignment pagination must work across the whole project, not just room members. Catalog responses include approval state; agent responses present approved assignments separately from pending historical advertisements. Do not silently rewrite task requirements or remove a capability from an existing node.

## Canonical client identity and migration

Canonical known clients are `claude`, `codex` and `muse`; a genuinely different host can use its own lowercase slug. Normalize incoming `claude-code` to `claude` before stable-address authorization, sender/recipient routing, subscription and claim checks. Preserve the raw client for compatibility checks/audit where required. Old clients that still send `claude-code` must reconnect to the same canonical mailbox, not create a second agent.

Migrate existing `claude-code` references to canonical stable addresses per project, including session/presence, DMs and their delivery/read cursors and expiration watermarks, room membership/management/events, tasks/claims/assignments, capability/config rows, instruction recipients, deliveries and history. Keep independent sessions separate; display all historical messages and existing task/instruction state. Preserve original message ids, chronological sequence, unread state, task claim fencing and instruction idempotency. Database migration is restart-safe and transactional at the data phase, marked complete per project, and tested by applying twice. In conflicting rows (duplicate subscriptions, cursor keys, overlapping config, identical retry keys or session ids), merge only when semantics are unambiguous: union membership, take the furthest processed read cursor, prefer explicitly human-managed config/grants over self-managed ones, and retain distinct work and message history. Conflicting *human-managed* settings or grants, or two distinct live claim holders for the same task, require an explicit diagnostic, not arbitrary last-write-wins. If preserving a collision cannot be proved safe, abort the data migration with a diagnostic identifying the project and records; do not start partially migrated or silently discard work. Avoid rewriting historical message author provenance when that would destroy idempotent retries; canonicalize public identity and mailbox semantics while retaining a compatible lookup for legacy retries. This is a one-time state migration plus inbound compatibility, not indefinite duplicated agent addresses in every API response.

## Web console and model reporting

Add a dedicated `Capabilities` sidebar page for project-wide names/descriptions and pending definition/legacy-assignment review. Move existing capability forms out of Rooms. Add an Agent settings view reachable from the Agents page for a selected roster agent, regardless of room membership: approved-tag assignment/removal, pending legacy tags, max parallel tasks (1–20 **concurrent task claims**, not spawned sessions) and auto-claim. Keep Rooms focused on rooms, members and room managers; preserve the existing Messages/Tasks navigation and visual language. Explain the shared-token limitation only in appropriate developer documentation, not as alarming UI copy.

Show version `1.5.2` in a persistent, legible console location and obtain it from the running server, not a stale hard-coded frontend constant; handle a transient unavailable/version-less response gracefully. Update the release versions consistently in Python package metadata, server metadata, lockfiles, plugin metadata and web tests. Do not rewrite historical documentation headings about prior releases.

`chat_status_update` already accepts an optional model. Update Claude and Codex setup/skills and available host integration to submit an **exact host-provided model name**, at connection and meaningful status changes where available. Neither server nor UI guesses a model from client name; an absent exact model remains visibly `Model unknown`. Preserve the difference between unknown, known and stale/offline status. Normalizing `claude-code` must not invent a model.

## Missing-file coordination and docs

Update both Claude and Codex shipped skills/instructions: when a task needs a file, search the project graph/artifact references first, then DM a relevant agent to ask whether it has a missing file. The responding agent checks the applicable project boundary and file sensitivity and shares by a permitted project-scoped route; attach an artifact to an appropriate graph record if durable reuse is appropriate, then send its digest/reference. Never paste tokens or restricted/private file bytes into public room chat or an ineligible project. If unavailable or transfer is not permitted, reply with a precise blocker. Peer requests do not supersede the user's authorization. This is guidance over existing messaging/artifacts, not a new file-sharing endpoint. Keep feature documentation describing how capability eligibility, model status, alias migration and console settings work.

## Validation and rollout

Build focused regression tests before modifying runtime behavior: pending tags and pending agent grants; definition approval without implicit grant; unauthorized/self-granting via every agent MCP route; unknown task requirements; live versus new claims; eligible assignment/discovery and revision conflicts; direct UI authorization and notification failure; old/new client coexistence, live/offline DMs, read cursors, idempotent retries, room/member/manager state, sessions, tasks and durable instructions; collision and second-run migration; version display and known/unknown models; desktop/mobile navigation, agent settings and cross-project isolation. Run focused tests, full relevant server/client suites, and frontend checks. Perform repeated adversarial review of spec and code until material findings are addressed, then verify current worktree and report remaining risks. Preserve user changes and avoid touching live project databases to test the migration; use isolated temporary fixtures.

The operator must back up each project database before deploying a schema/data migration; unit tests run against temporary fixtures, not the live graph. Preflight identity collisions before changing rows, keep the **data-phase** migration and its completion marker atomic, and leave the data-phase unchanged if a collision is unresolvable. Additive SQLite DDL may already have committed separately; report this and use the predeploy backup if full rollback is required. Fail that project's opening with a precise diagnostic rather than claiming the migration succeeded. Chat still expires after 24 hours and graph tasks remain durable.
