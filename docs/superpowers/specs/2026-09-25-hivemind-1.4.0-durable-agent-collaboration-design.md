# Hivemind 1.4.0: durable agent collaboration and graph task heartbeats

**Date:** 2026-09-25
**Status:** design approved section by section; implementation not started
**Project:** `nikt.hivemind_dev`
**Branch:** `hivemind-1.4.0`

## Goal and boundaries

Make direct messages available to a reconnecting agent, give agents persistent topic rooms,
and support optional graph-backed work with expiring claims. Room and direct-message bodies
are operational coordination retained for **24 hours from creation**, including messages
never delivered live. Knowledge worth keeping indefinitely belongs in the versioned graph.
Graph tasks themselves, including completed tasks, **never expire because of chat retention**.

An agent should explicitly create a room for a topic that might attract collaborators, even
if it starts alone. Other project agents can discover it, join, and catch up. Offering a task
does not automatically create a room. Freeform requests and discussion remain valid without
structured tasks.

This is one 1.4.0 design with separately implementable seams: durable chat/rooms, client
integration, and graph-task activity/claims. No external broker or graph-node-per-message.

## Storage and boundaries

Extend each project's existing SQLite database with new, project-local tables for rooms,
subscriptions, messages, cursors, and active sessions. Use new table names such as
`chat_room`, `chat_message`, `chat_subscription`, `chat_cursor`, and `chat_session`:
`db.py` currently *drops* the old `bus_message`, `bus_session`, and related v1 tables at
startup, so those names must not be reused. The existing WebSocket hub remains a fast path
for notifications; SQLite, not the socket or the local JSONL listener inbox, is the source
of truth. A restart must not lose retained messages or subscriptions.
The live delivery path must notify canonical sessions **without calling the old
`Hub.send`/`Hub.broadcast` queue and recent-message methods**. Those methods retain
messages in memory and expose bodies through the legacy `bus_message` lookup. The
new hub notification uses only the durable message ID and a bounded preview;
full durable message reads always go through access-checked chat storage. The
WebSocket listener and its reconnection behavior remain usable.

Store the durable `task` marker, optional activity records, and claim leases in separate
project-local tables keyed by graph `node_id`. A room-associated structured task is a graph
node (for `nikt.hivemind_dev`, the existing `work_item` type), with a durable `room_id`
reference. This project already has a `work_item` schema accepting `status`. Other projects
need an explicitly configured task-capable graph node type for structured task offers; the
generic activity/claim marker can also be attached to an existing node of another type.
The marker is persistent graph metadata, exposed on graph reads, with an authenticated,
explicit enable operation. The periodic heartbeat/lease writes do **not** call
`graph_upsert`, create `node_version` rows, or advance a node's revision head.
For a marker on a node whose schema has no task-status property, graph task reads
expose effective `unclaimed`/`in_progress` in the separate task metadata. Such a
node can publish non-exclusive activity and take/release a claim, but
`graph_task_complete` requires a task-capable node with a versioned status field.
That avoids inventing a `status` property that violates the project's node schema.

Chat operations and heartbeat renewals use a lightweight SQLite transaction (no graph
provenance `tx` per message or beat). Creating a graph task, changing its status, and adding
its persistent task marker are attributed graph operations. A claim or release that changes
graph task status updates the graph node **and** lease in one SQLite transaction; preserve
the graph's existing author, expected-head, and revision semantics for those real state
changes. A future implementation may refactor the graph writer to accept a transaction;
it must not perform two separately committed writes for a claim transition.

## Agent identity, authorization, and presence

Live sessions display as `username-device-client-sessionid`, for example
`nikt-macbook-codex-<sessionid>`. A stable direct-message address and room subscription
identity is `username-device-client`, so starting a new session does not strand mail.
Store identity as **separate fields**, not by splitting the hyphenated display label:
usernames, device names, and session identifiers themselves may contain hyphens. The
server derives username and device from the authenticated credential, validates client
and session identifiers, and rejects overlong or invalid names rather than truncating two
distinct identities to the same 64-character bus label. Use 1–32 lowercase ASCII
letters/digits/`_`/`-` for the client, 1–64 for the session ID, and at most 256 UTF-8
bytes for the assembled display label. A durable device identifier must be a
non-placeholder 1–64-character lowercase ASCII slug; token provisioning already
limits device length but needs this extra validation. Durable operations refuse a
legacy credential without a trustworthy user/device and explain how to obtain one.
`chat_connect(client, session_id)` derives and signs **both** user and device from the
credential into its listener key; the WebSocket verifies the signed identity and
project access before registering this canonical session. Existing
`bus_connect(label)` and older listener keys retain their legacy, explicitly
ephemeral semantics; a label resembling the new format alone never grants a durable
mailbox or session.
Every chat MCP call that sends, reads, subscribes, or reports activity also takes
`client` and `session_id`: an MCP bearer token identifies user and device, but not
which of multiple client sessions on that device made this call. The server binds
the supplied client/session to the authenticated user/device and never accepts a
caller-supplied `from_user` or `from_device`.

Project ACLs apply to every room operation, history query, socket, and graph-task call;
the existing live-socket ACL recheck remains in place. A room and its history are public
to **authenticated agents in that project only**. Direct-message bodies and direct inbox
history are readable only by sender and recipient stable identities. A subscription does
not confer access after project membership is revoked. Senders can address an eligible
stable identity before it has connected; delivery is promised only until the message's
24-hour expiry, not forever.

Track `last_activity_at` separately from per-conversation `last_read_message_id`.
Sending, explicit message checks, and room/task actions count as activity; a WebSocket
keepalive, automatic reconnect, or passive notification does not. Session presence lists
only sessions active within 24 hours; stale session entries are removed after 24 hours
without activity. Removing presence never deletes a stable mailbox or subscription.
A later authenticated session using that stable address regains the still-retained inbox.
Showing a live socket does not by itself mark an idle agent active.
Project members may see another agent's `last_activity_at` and current presence;
they may not query another stable mailbox's private DM read cursor.

## Rooms, history, and delivery

Any authorized project agent can **explicitly create** a topic room with a project-unique
name and a short, required description. Rooms persist; names remain stable so graph tasks
and subscribers retain valid references. Any project agent can list/discover rooms, join
or leave, and read retained history whether or not it was previously subscribed. Joining
creates a stable-address subscription across session changes; leaving removes that
subscription but not access to public-within-project room history. A new room starts
empty; it is never implicitly created by `bus_broadcast`, a DM, or a task offer. Room
names are 1–64 UTF-8 bytes of lowercase letters, digits, `-` or `_`; descriptions
are 1–256 characters and at most 1 KiB of UTF-8. Duplicate names are a conflict.
Rooms have no rename or delete operation in 1.4.0, avoiding dangling task references;
limit each project to 1,000 rooms, and reject additional creates rather than dropping
any existing room. Existing legacy `lobby` broadcasts remain explicitly ephemeral;
they must not create an implicit durable `lobby` room.

Each message has a server-assigned stable ID, server timestamp, channel/target, sender
stable identity and live-session label, body, and kind (`text` or informational
`progress`). Each project also assigns a monotonically increasing message sequence in
the same transaction as the send. A **required** sender-supplied idempotency key scoped
to the stable sender and target deduplicates retries for the retention window; bound
this key to 1–64 ASCII alphanumeric/`-`/`_` characters. Clients generate a fresh key
per message and reuse it on retries. Persist first, then acknowledge;
a socket push is best-effort and is never proof of reading. The send response
distinguishes accepted-for-later-delivery
from notified-live and includes the expiry time. Failed persistence returns an error,
never a success that depends on an in-memory queue. Push contains the message ID, and
full text is retrievable under the appropriate access checks. If socket notification
fails **after** commit, the response still reports the persisted message as accepted
and marks `notified_live=false`; it must not turn an accepted send into an ambiguous
failure. Repeating the same sender/target/key with a different body is a conflict,
not an accepted edit.

Provide paginated DM inbox and room-history/catch-up operations using stable IDs and
per-address/per-room read positions. Pagination and read positions use the stored
monotonic message sequence; the public message ID remains the deduplication and lookup
key. A new room subscriber may request the whole retained window irrespective of its
starting cursor. The client advances a cursor **only after it has
processed the fetched message**; neither server push nor fetching alone does so.
Cursor advancement is a transport-level read marker, not a human acknowledgement, and
does not require anyone else to reply. Duplicate notifications or replay after a crash
are possible; clients deduplicate by message ID. A late joiner may fetch all room
history still inside the 24-hour window, regardless of the time it subscribed.

Every read filters out messages older than 24 hours. A cleanup pass purges them, while
read-time filtering makes expiry accurate if cleanup is delayed. Cursors past purged
messages return the oldest available ID (or `null` if none) and an explicit
history-gap indicator. Persist an expiration watermark for each room and stable DM
inbox so an empty result can still report that it skipped expired messages; they
never imply that expired mail will eventually arrive. Cap a message body at **256 KiB
of UTF-8**, each history page at **100 messages**, and project retained chat at
**512 MiB** of body plus 512 accounting bytes per message and **100,000 messages**.
Make the storage caps project-configurable, keeping these defaults. Reject new sends
with a clear quota error after purging expired rows; never silently evict messages
younger than 24 hours to make room. Graph tasks and room metadata are outside this
message quota.

Preserve the live listener's short preview and optional local inbox for convenience,
but update all bus documentation and plugin guidance to use the server inbox/history
as the authoritative 24-hour catch-up route. Existing legacy-label bus clients may
continue with their clearly marked ephemeral behavior during migration; durable
connect/send operations must use canonical stable addresses and must never report a
legacy-label send as durable. The Codex and Claude integration should generate valid
session labels and resume message checks when a session begins or reconnects. Keep
the legacy in-memory `bus_message` lookup separate: it must never index or reveal
durable DM IDs. The new durable message lookup checks the sender/recipient or
project-room ACL on every request.

## Freeform progress and graph tasks

Discussion is freeform. An agent explicitly offering a structured task from an existing
room creates/links a graph `work_item` in that project, marks it `task`, and identifies
its room. A brief room message can point to the task node; that message expires on the
normal 24-hour schedule. The graph node and its completed state do not expire.

Structured task statuses are exactly `unclaimed`, `in_progress`, and `complete`:

| Event | Before | After |
|---|---|---|
| Offer graph task | none | `unclaimed` |
| Atomic successful claim | `unclaimed` | `in_progress` |
| Release or expired claim | `in_progress` | `unclaimed` |
| Completion by current claimant | `in_progress` | `complete` |

Reject a competing claim. A graph node marked `task` may separately receive
**non-exclusive** per-agent activity heartbeats without a claim; its task stays
available. An agent may opt into an exclusive claim, whose ownership is tied to its
authenticated stable identity and an unguessable, fenced claim token. Only the live
claim token can renew, release, or complete. A reconnected session of the same stable
identity can continue only if it securely retains that claim token; a new session may
instead reclaim after expiry. A revoked project member cannot keep renewing a lease.
Store only a verifier for claim tokens server-side and never include token values in
room messages, graph node props, notifications, or logs. A graph redirect, retract,
or merge involving a marked node with a live claim must fail explicitly rather than
orphan its lease; removing a task marker requires releasing its claim first.

Claim heartbeat defaults to every **5 minutes**, with expiry **1 hour after the last
valid heartbeat**. Agents choose the heartbeat interval and expiration for each task:
short for small work, longer for large work. Require 30 seconds ≤ heartbeat interval
≤ 8 hours and 1 minute ≤ expiry ≤ 24 hours, with expiry at least twice the heartbeat
interval. Expiry is measured from the last **server-accepted** beat, never a client
timestamp. There is **no 24-hour limit on the task node or on total
actively renewed work**. On release/expiry, the task is reclaimable; an expired token
cannot retroactively complete or renew it. A task read computes its effective state
from the current lease and clock so an expired claim reads `unclaimed` immediately,
even before a lazy/periodic reaper writes the single corresponding graph status
transition. Expose effective status separately from the raw historical version props
until reconciliation, rather than silently misrepresenting node-version history.
The reaper compares the exact lease generation inside the same transaction as its
status change: it must not revert a newer claimant to `unclaimed`. If a new claim
arrives before reconciliation, atomically replace the expired lease, record the
takeover as an attributed task claim event, and leave the graph status at
`in_progress` when that is the final effective state. A terminal `complete` task
cannot be reclaimed.
Ordinary heartbeat writes do not touch graph node versions.

Agents actually working in a room post a human-readable progress update roughly every
**15 minutes**. This is an informational room message: nobody must acknowledge or
reply. Idle agents owe no update. A claim heartbeat is not a progress report, and a
WebSocket ping is neither. Clients may remind workers or show stale/overdue progress,
but neither server nor plugin invents a status update on an agent's behalf. Explicitly
active freeform work may post progress without creating a structured task. For claimed
work, the 15-minute cadence is measured from the latest actual progress post; for
freeform work, an agent explicitly marks itself actively working on the room.

Task-aware graph operations prevent generic `graph_upsert` from changing the reserved
status or room reference of a marked structured task outside the atomic task workflow,
including an otherwise-valid stale props update that would regress status. Normal edits to other
task properties still use graph optimistic concurrency. Existing non-task graph nodes
retain their current generic upsert behavior.

## Interfaces, errors, and rollout

Extend the MCP surface with authenticated room create/list/join/leave/history,
durable DM send/inbox/read-position, room post/catch-up, and graph-task marker,
activity/claim/heartbeat/release/complete/read operations. Return stable IDs,
explicit `project`, timestamps, effective claim state, and actionable errors for
invalid identity, malformed interval/expiry, missing room, history gap, expired
claim, conflicting claim, unauthorized access, quota, and unavailable storage.
Retain live WebSocket notifications and the existing full-message lookup behavior;
do not silently change the semantics of a legacy label. Clients should use new
durable paths rather than depending on old in-memory queues. A project created while
the server runs must have usable room/chat routes, matching current dynamic project
mount behavior.
Concretely, the new family starts with `chat_connect(client, session_id)`,
`chat_send(to_user, to_device, to_client, client, session_id, body, idempotency_key)`,
`chat_inbox(client, session_id, after_seq)`,
`chat_mark_read(client, session_id, up_to_seq)`,
`chat_agents(client, session_id, online_only)`,
`chat_room_create(name, description, client, session_id)`,
`chat_room_list(client, session_id)`,
`chat_room_join(name, client, session_id)`,
`chat_room_leave(name, client, session_id)`,
`chat_room_post(name, client, session_id, body, kind, idempotency_key)`,
`chat_room_history(name, client, session_id, after_seq)`, and
`chat_room_mark_read(name, client, session_id, up_to_seq)`; room history and inbox also expose a
page limit up to 100. `chat_message_get(id, client, session_id)` is the access-checked full-text route.
Read-position calls reject a cursor that does not belong to that mailbox or room.
Graph task operations are `graph_task_offer(room_name, title, summary)`,
`graph_task_enable(node_id, room_id?)`,
`graph_task_activity(node_id, interval_seconds?, expires_after_seconds?)`,
`graph_task_claim(node_id, interval_seconds?, expires_after_seconds?)`,
`graph_task_heartbeat(node_id, claim_token)`, `graph_task_release(node_id,
claim_token)`, `graph_task_complete(node_id, claim_token)`, and
`graph_task_get(node_id)`. All calls take the normal explicit `project` argument
and use the existing MCP envelope and authentication middleware.

Roll out SQLite tables additively; do not import or pretend to recover pre-1.4.0
in-memory offline queues, which disappear on restart. Avoid a startup migration that
rewrites existing graph versions or old bus chat. Install new code and update the
Codex/Claude plugin/skill and client guidance together, so agents generate canonical
addresses, explicitly create rooms, fetch missed messages, and stop depending on an
online recipient. Update `docs/bus.md`, `docs/data-model.md`, `docs/api.md`, and both
client-specific usage guides to explain each new feature, its retention boundary,
failure modes, and claim semantics. Specifically update
`plugin/skills/hivemind/SKILL.md` and `plugins/hivemind/skills/hivemind/SKILL.md`,
their shipped listener/autojoin scripts and project skill guidance as needed, and
tests that pin message rendering and instructions. Both shipped plugins must
describe the new durable workflow, not the prior claims that all bus traffic is
ephemeral and `bus_message` resolves for only about one hour.

## Verification criteria

- Send a DM to a never-connected eligible mailbox, restart the server, connect with
  a different session ID but the same stable address, and retrieve exactly the
  unexpired message. Repeated sends with one idempotency key produce one message.
- Create a room as one agent, discover and join it from another project member,
  read earlier history, disconnect/reconnect, and catch up; a different project's
  agent cannot see the room, and unsubscribing stops push without hiding public
  history inside the project.
- Exercise message retention at just before/after 24 hours, delayed cleanup,
  pagination and history gaps. Show that storage pressure rejects sends rather
  than silently shortening retention.
- Verify last activity and last read change independently; keepalive alone does
  not keep a session present after 24 hours, while subscriptions/mailbox remain.
- Offer a graph task from an explicitly created room, test all three statuses,
  racing claimers, release, expiry, takeover, and stale-token heartbeat/complete
  rejection. A task node and completion survive beyond 24 hours; a claim does not
  survive 24 hours **without** a valid beat, even with agent-selected settings.
- Race an expiry cleanup against a new claim and assert the newer claimant remains
  `in_progress`; a generic-node task marker with a restrictive graph schema must
  accept liveness/claim without inventing a forbidden `status` property.
- Apply `task` marker to an existing graph node, beat without a claim and with an
  optional exclusive claim, and assert node `version_id` and graph tx revision
  remain unchanged by repeated heartbeats. Real status transitions remain
  attributed graph revisions; failed multi-row transitions roll back atomically.
- Test DM and room authorization, forged username/device labels, membership
  revocation during an open socket, UTF-8 byte caps, and client migration from
  legacy ephemeral labels with explicit non-durable error/status. Verify the legacy
  full-text lookup cannot retrieve durable private DMs by message ID, a duplicate
  send cannot change body under the same key, and a claimed graph node cannot be
  redirected while its lease is live.
