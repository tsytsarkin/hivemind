# Hivemind 1.5.0: project console and agent teams

**Date:** 2026-09-26

**Status:** design approved; user authorized adversarial review and implementation

**Project:** `nikt.hivemind_dev`

**Branch:** `hivemind-1.5.0` (based on the unmerged 1.4.0 feature branch)

## Goal and scope

Ship a polished, optional web UI on a **different port** from Hivemind's MCP server. A human signs
in with an existing Hivemind user token, chooses one of the projects they can access, and can see
that project's agent presence, rooms, messages (including DMs), graph task statuses, and queued
instructions. The UI lets them DM an agent, create rooms, manage room membership and managers,
assign work, and send an agent an instruction such as "queue up work for this room." Agents can
also become room managers through MCP without a browser approval step.

The UI is available to **any authenticated user who has access to the selected project**, not only
its owner or a server operator. Existing access rules stay intact: private projects admit owner
and members; shared projects admit every authenticated user. UI access never grants access to a
different project. A project's DMs are explicitly visible to all its users in the console; this
is an intentional expansion of visibility **in the UI only**. Existing agent-facing DM reads
remain sender/recipient restricted. Indicate the project's DM visibility clearly in the UI.

This is one 1.5.0 feature with separately testable seams: UI listener and browser auth, console
and project-wide reads, room teams and graph assignments, agent capabilities, and project-local
instruction queues.
Implement on top of the durable rooms/chat/graph tasks from 1.4.0. Do not rewrite historical
1.4.0 design documents or silently treat its unmerged branch as already present on `main`.

Out of scope: password accounts, global cross-project administrator powers, remote shell/process
execution, spawning/killing agents, cross-project instruction feeds, extending ordinary chat
retention beyond 24 hours, implicit room creation, and guaranteeing that an offline agent actually
runs work. A mandatory assignment is a server-enforced reservation plus a documented agent
obligation; the server cannot force the agent process to execute.

## Configuration and deployment

Serve the UI and its browser API/live updates from a second listener in the Hivemind deployment;
MCP remains on its configured host/port. The default UI listener is `127.0.0.1:8788` and is
**enabled by default**. Add an optional `<data-dir>/hivemind.toml` with a `[web_ui]` section:

```toml
[web_ui]
enabled = true
host = "127.0.0.1"
port = 8788
```

Missing file/section means those defaults. A documented `HIVEMIND_CONFIG_FILE` may select another
file; `HIVEMIND_UI_ENABLED`, `HIVEMIND_UI_HOST`, and `HIVEMIND_UI_PORT` override the file for
deployments already using environment configuration. Reject invalid booleans, ports, identical UI
and MCP bind addresses, and malformed TOML with an actionable startup error; never fall back to
the MCP port. With `enabled = false`, open **no** UI socket, run no UI background job, and leave
MCP behavior unchanged. With `HIVEMIND_REQUIRE_AUTH=0`, do not expose the UI: log that the
token-authenticated UI is unavailable in unauthenticated mode, while keeping MCP available.
Document binding to a private interface or putting TLS in front before exposing the UI beyond
loopback; the existing bearer-token transport is not encrypted by Hivemind itself.

The 1.5.0 implementation bumps the workspace, server, client, exposed server version, lockfile,
and Claude/Codex plugin package manifests where their version denotes the Hivemind release.
Update current usage docs for the new behavior; leave old design/history/version examples whose
meaning is specifically about 1.4.0 intact. A plugin's independent *skill* version need only
change when its actual instructions change.

## Browser authentication and project boundary

The login form accepts a **server-level Hivemind user token**, not a legacy single-project token
or new username/password. Validate against the existing `IdentityStore`. Exchange the submitted
token for an opaque, random, server-side browser session and an `HttpOnly`, `SameSite` cookie;
mark the cookie `Secure` under HTTPS, and support local HTTP only as an explicitly documented
loopback/development case. Do not place a raw token in a URL, local storage, browser JavaScript
state after login, or logs. Store only a token fingerprint with the server-side session and
revalidate the credential on every request, so deleting/revoking the token invalidates the UI
session immediately. Bound idle and absolute session lifetime; sign-out revokes the session.
Require origin checks and a per-session CSRF token for every state-changing browser request.
Rate-limit failed logins. Set a restrictive content-security policy; escape untrusted chat,
graph, and instruction text. Browser session cookies are scoped by hostname, **not port**:
MCP on the same hostname may receive the otherwise-unused cookie, so neither listener may log
Cookie headers and both ports must run under the same trusted host boundary.

The UI root and login cannot reveal private project names. After login, list only projects
returned by the existing `can_access` rule. Every browser API/read/push request naming a project
re-evaluates both session identity and project ACL; missing and forbidden projects get the same
response. An authorization change ends live subscriptions within 30 seconds and denies subsequent
requests. Keep browser endpoints on the UI origin; the browser never needs cross-origin calls or
its user token sent to the MCP port. Project data lives in existing per-project stores; browser
sessions alone live at server level and contain no project content.

The UI request wrapper publishes the resolved identity in the same per-request context used by
graph write attribution, and clears it before any early return; a browser request must never
inherit another user's identity in in-process clients or concurrent requests.

Expose explicit project-scoped *console transcript* reads for room and DM history; do not weaken
`ChatStore`'s existing per-address agent DM inbox API. Log project-wide DM access and security
sensitive writes without logging message/token bodies. Resolve user and device from the
authenticated token, not client-supplied sender fields. Browser-created DMs have an identifiable
human/web sender and a stable reply address; use the user's validated device and a reserved web
client name, never an invented agent identity. Persist a server-assigned browser-origin marker so
an agent that happens to share a user/device token cannot masquerade as a human merely by picking
the same client name. If a user token lacks a usable device, show how to mint a device-bearing
token before allowing chat sends; reads remain accessible.

## Agent roster, rooms, and conversation UI

Rooms retain their explicit names and required short descriptions; never create one implicitly
on assignment, instruction, or DM. A project user can create a room and add/remove known,
project-local stable agent addresses `(user, device, client)`. Validate existence/eligibility;
never infer a stable identity by splitting the hyphenated session display label. Ordinary agents
retain 1.4.0 self-join/leave behavior. Membership survives session changes and a 24-hour inactive
session cleanup. Removing an agent from a room removes its membership, not historical messages
or existing graph task/audit records; it vacates the manager slot if that agent was manager.
Reject removal while the member holds a waiting assignment or live claim in that room until a
project user/manager explicitly reassigns or cancels/fences that work. Do not strand reserved
tasks by silently removing their eligible assignee.

The roster shows each stable agent, active session labels
`username-device-client-sessionid`, room memberships, last meaningful activity, and an online /
recent / offline indicator. Define online from a current authenticated connection or recent
explicit activity/heartbeat, not from room membership or passive notification alone. Show the
exact last-seen time and do not label an agent with only an old subscription "online." Remove
sessions inactive for 24 hours from the active roster, but still show subscribed offline agents
in their rooms so users can manage them. Do not silently purge room membership, last-advertised
capabilities, or task ownership.

Browser DMs address stable agent identities; a session change does not strand the mailbox.
Persist and notify through the same 1.4.0 durable-chat path, with idempotent sends, pagination,
offline catch-up, and the existing **24-hour** message expiry. Room history likewise shows only
retained messages; display a history-gap/expired indicator instead of implying older data can be
fetched. Browser reads of all project DMs use the explicit console route above. Read markers are
per actual browser/human address and must not move an agent's private cursor. The DM composer
reminds users that everyone with project access can read project DMs.

## Per-room managers and graph task assignments

Store a single manager stable address per room in project-local metadata, with transactional
promotion/handoff events. Any project user may designate a room member in the UI. An agent that
is a member of that room may promote **itself** through MCP with a valid project-access token;
the server binds the user/device to that token and cannot accept a forged "promote another agent"
identity from the call. It does **not** demand separate human approval: a user request in an
agent's conversation is not independently verifiable by the server. A new promotion atomically
replaces the previous manager and records who/what/when. A vacated role may be filled later.
Changing managers never cancels already assigned work. This manager label coordinates teams; it
does not create a new project ACL or grant cross-project access. An MCP caller supplies the
client/session part of its address, so the server can validate a current session and room
membership, but cannot cryptographically distinguish two clients sharing one user/device token;
audit must not pretend otherwise. Mint distinct device credentials when that distinction matters.

Any project participant may create or break down a graph task. Use the project's existing
task-capable `work_item` schema when it supports the required status transitions; when it does
not exist or is incompatible, provision a reserved built-in collaboration task node type
additively in that project as a server-owned bootstrap/migration, never as an agent-approved
schema change. Never overwrite or silently widen a project's custom `work_item`
schema. Both forms are graph nodes with durable task markers and room references; assigning an
existing marked task remains supported. This ensures task creation works in *every* project,
not only `nikt.hivemind_dev`, without treating chat messages as task records. The room manager,
or a human project user in the UI, can assign a room task to a room member. This is **mandatory,
not an offer**: the assignee cannot decline, and another agent cannot claim its reservation.
Add project-local assignment metadata beside `graph_task`, not
ephemeral chat records or a fabricated graph node version per heartbeat. The graph task retains
the existing `unclaimed` / `in_progress` / `complete` status contract; the UI derives an
`assigned / waiting` view from an unclaimed task with an assignee. An assignment changes graph
task metadata and produces an attributed, durable event in a single transaction; concurrent
assignments require compare-and-swap or equivalent fencing.

While the assignee is offline, its task is reserved as `assigned / waiting` **without starting a
heartbeat or expiry timer**. When that agent checks in, it sees its assignments through MCP and
explicitly starts one via a fenced claim; then status becomes `in_progress` and the existing
configurable heartbeat/expiry begins (5 minutes / 1 hour by default, max 24-hour expiry).
Enforce the reservation in *all* claim paths so other agents cannot take it while waiting.
A manager/project user can cancel or reassign a waiting assignment, including one stranded by an
agent's disappearance. An expired in-progress claim is **effectively** available immediately;
the existing reaper or next claiming transaction persists the `unclaimed` status and clears the
assignee without producing a heartbeat revision. Stale holders cannot complete, beat, or report
progress against the new generation. Reassigning an active task must first revoke/fence its old
lease atomically and show the displaced agent in audit. Completed task records remain in the
graph without chat TTL.

## Self-advertised capabilities and task eligibility

Each project persists a stable agent address's **self-advertised** capabilities independently of
other projects and independently of its expiring chat sessions. An agent replaces its own set
through an authenticated MCP tool; the server binds user/device to its token and validates a
current client/session, but a token shared across clients cannot attest which process claimed
the client name. Never allow one project user to register another user/device's capabilities.
Show names and the last advertisement time in the UI with a "self-reported" label; a browser
user may inspect them but not impersonate the agent by editing them. Normalize and bound tags
(lowercase ASCII slugs, at most 64 per agent); use exact-name matching, not vague substring,
role, or tool-description inference. Absence of an advertisement means an empty set.

Every marked graph task may have an optional bounded `required_capabilities` list (at most 32
distinct tags) in project-local task metadata attached to its graph node. Surface the list on
task graph reads and in UI/MCP task offer/enable/read operations; changing it is an attributed
task event, not an untracked chat message. No required tags means any otherwise eligible agent
can claim. For a nonempty list, assignment and **every** claim path require all tags in the
agent's current project-local advertisement. Apply the check atomically with assignment/claim
to avoid a race with capability updates, including legacy/general claim operations. Ineligible
agents are visibly filtered or marked in the assignment UI and receive a clear MCP error.

When an agent removes a tag needed by a waiting assignment, unassign it and return the task to
available. When an in-progress holder loses a needed tag, revoke/fence its lease, update task
status to available, and audit the reason in the *same transaction* as the advertisement change;
stale claim tokens can neither beat nor complete. Changing a task's requirements triggers the
same immediate reevaluation. Offline status alone does **not** erase an advertisement: an
offline agent can remain eligible for a mandatory waiting assignment until it checks in, at
which point it may update its capabilities before it starts. Since declarations are self-reported,
server eligibility checks do not independently prove competence.

## Project-local human instruction queue

Keep a **separate durable queue in each project's SQLite database**, not in chat, the old live
bus, or a server-global queue. A human project user can address a freeform instruction to an
agent stable address or to the current manager of a particular room (resolve and record the
actual recipient at enqueue time). Example: ask that manager to create and assign several graph
tasks. An instruction is not an OS command or authority to run shell code. The UI shows its
author, recipient, optional room, timestamps, status, and final reply/error; MCP lets the
recipient list/check in, acknowledge, start, and resolve it. Never allow another project's
agent/credential to fetch or update the instruction, even if its address text matches.
On manager handoff, move still-queued instructions addressed *to the room manager* to the new
manager with an audit event; direct agent instructions do not move. Leave acknowledged/started
instructions with the original recipient and show when a manager-dependent action can no longer
be completed; the user can explicitly retry it for the new manager. Never silently run one
instruction twice across a handoff.

State transitions: `queued -> acknowledged -> in_progress -> completed | failed`. An agent may
complete directly after acknowledgement for short requests. Use server-issued IDs, bounded
bodies and paginated reads, idempotency keys for enqueue/retries, atomic recipient/state checks,
and compare-and-swap transitions so reconnects do not duplicate acknowledgement or outcomes.
An unhandled instruction **does not expire after 24 hours**. Surface unacknowledged or started
instructions that become stale when their agent is inactive; do not automatically replay an
already-started instruction and cause duplicate side effects. A user can cancel an unstarted
instruction or explicitly retry a failed/stalled one, with a new attempt/event linked to the
original. Retain terminal outcomes for at least 30 days; bound project storage and reject new
instructions with a clear quota error instead of silently evicting unresolved work. Persist
author/recipient/status audit metadata beyond body retention. A queued instruction counts as
work waiting for an agent, not an ordinary DM, and therefore has its own UI view. Agent-reported
acknowledgement/outcome reflects the agent's report; it cannot prove a requested external action
occurred without separately recorded evidence.

## UI composition and accessibility

After login, the project switcher prominently names the active project; never blend projects'
rooms, messages, or instruction queues into a single view. Provide Overview, Rooms, Agents,
Tasks, and Instructions views. Overview summarizes online agents, waiting assignments, overdue
task heartbeats, and queued/stale instructions. Room detail has a retained message timeline and
a contextual panel for description, members, manager, and graph tasks. Agent detail displays
last seen, self-reported capabilities, memberships, assigned work, and a human-to-agent DM
composer. Forms support create
room, add/remove room members, choose manager, assign/reassign work, and issue an instruction;
destructive or displaced-claim actions show their target and demand explicit confirmation.

Use a cohesive light/dark palette, strong typography, accessible status contrast, readable
empty/loading/error states, and keyboard-accessible navigation and forms. Include relative and
absolute times, project-visible DM warning, expiration gaps, unread counts, and explicit status
chips. On narrower screens, switch project/room navigation and context panels into accessible
drawers while retaining access to every action. Deliver current information with a same-origin
push or bounded polling fallback; reconnect without inventing an "online" agent or advancing a
read cursor before the browser actually processes a message.

## Error handling, migration, and verification

Migrate existing project SQLite databases additively and transactionally; migration must not
rewrite 1.4.0 message history or claim generations. New empty projects get the same tables.
Restart preserves room managers, assignments, queues, outcomes, and browser sessions only while
their underlying token remains valid. If a room manager is removed, make the vacancy visible;
if a recipient is offline, display queued/waiting rather than an apparent delivery success; if a
UI port is occupied, report the listener error instead of silently binding MCP's port. Browser
mutations return actionable conflicts for stale handoffs/claims and retry-safe responses where
their idempotency keys match. Keep failures after durable commits from turning an accepted write
into an ambiguous duplicate on retry.

Tests must cover: UI enabled by default/disabled by config (including no listener), per-user
project enumeration and cross-project denial, private versus shared projects, session expiry and
token revocation, CSRF and XSS/unsafe content, DM project-wide UI viewing without broadening
agent MCP reads, room membership and simultaneous manager promotions, offline assignment versus
claim start, lease expiry/fencing and manual reassignment, capability registration and project
isolation, missing/mismatched required capabilities through ALL claim paths, capability loss
while assigned/claimed, changed task requirements, queue isolation/idempotency/restart/
stalled status, session cleanup without membership loss, chat's 24-hour history gaps, and the
1.5.0 version surfaces. Exercise real login, navigation, mobile layout, DM, room management,
assignment, instruction completion, and error states in browser-level smoke tests. Update the
Claude and Codex skills/guides together so an agent learns manager promotion, mandatory
assignments, task heartbeat, capability advertising and eligibility, project-local instruction
polling, and where the UI fits; document explicitly that UI control never means remote process
control.
